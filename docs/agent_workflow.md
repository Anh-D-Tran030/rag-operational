# Agent Coding Workflow — Architecture and Usage

How the agentic coding harness in this repository is built, why it is shaped
this way, and how to drive it.

This document describes what is **actually installed in this project**, verified
by reading the files. Where the installed setup diverges from the generator that
produced it, that is called out in [§9 Known gaps](#9-known-gaps-and-caveats)
rather than glossed over.

---

## 1. What this is and where it came from

The harness was originally generated by a global Claude Code skill. Its runtime
control plane is now repository-owned under `.agent-context/`, so the global
generator and Claude Code are historical provenance rather than dependencies. It scaffolds a
"self-improving agent pipeline" into a project: a gate state machine, an
inter-agent message bus, two tiers of memory, a skills engine, and — most
importantly — hooks that check the agent's work automatically.

Its organising idea is that a harness needs two kinds of control, and works
with neither alone:

| Kind | What it does | Where it lives here |
|---|---|---|
| **Guides** | Steer *before* the agent acts. Raise the odds of getting it right first time. | `AGENTS.md`, `.agent-context/agents/`, `.agent-context/pipeline-contract.md`, `project.md`, `conventions.md`, `domain.md`, `examples/` |
| **Sensors** | Observe *after* the agent acts. Let the agent correct itself before a human looks. | `critic_gate.sh` (Stop hook), `run_tests.sh`, sandbox/approval policy |

Guides are the easy half and the useless half on their own: a harness that is
all contract and no sensor cannot tell you it has stopped working, and the
failure is silent because nothing was ever checking. That is why the Stop hook
runs the **real test suite** on every turn end rather than trusting any agent's
claim about test results.

## 2. Architecture at a glance

```
                      ┌──────────────────────────────────────────┐
                      │  GUIDES (read before acting)             │
                      │  AGENTS.md ── every session              │
                      │  agents/<role>.md ── selected gate role │
                      │  pipeline-contract.md ── pipeline only   │
                      │  project.md / conventions.md / domain.md │
                      │  examples/ ── real files to imitate      │
                      └────────────────┬─────────────────────────┘
                                       │
   ┌───────────────────────────────────▼─────────────────────────────────┐
   │  TWO LANES — same sensors, different bookkeeping                    │
   │                                                                     │
   │  Fast lane (default)          Full pipeline (named work)            │
   │  edit → verify                PLAN → EXPLORE → BUILD → TEST → REVIEW│
   │  no .agent-context/ writes    gate artifacts + status.json + run_id │
   └───────────────────────────────────┬─────────────────────────────────┘
                                       │
                      ┌────────────────▼─────────────────────────┐
                      │  SENSORS (run after acting, every turn)  │
                      │  Stop hook → run_tests.sh → red? block   │
                      │  policy/sandbox → .env, git push, …      │
                      │  PostToolUse → episodic log              │
                      └────────────────┬─────────────────────────┘
                                       │
                      ┌────────────────▼─────────────────────────┐
                      │  MEMORY & LEARNING                        │
                      │  episodic JSONL ──(reflector)──► semantic │
                      │  skills/ ── promoted only after success   │
                      └───────────────────────────────────────────┘
```

The critical property: **lane selection changes only what gets *written*, never
what gets *checked*.** The checks live in hooks, not in the contract. That is
what makes a fast lane safe rather than a loophole.

## 4. How the mechanisms work

### 4.1 Two lanes

**Fast lane** is the default and covers most work: bug fixes, config changes,
small patches. No `plan.md`, no `status.json` write, no `run_id`. Edit and
verify.

**Full pipeline** is for a new module or a named Gate. The agent reads
`pipeline-contract.md` and follows the gate protocol.

The reason for the split is practical: charging a one-line fix the full
five-gate ceremony does not make it safer, it makes the pipeline get bypassed
entirely — which is strictly worse than having a cheap lane.

### 4.2 The gate state machine

```
pending ──► ready ──► in_progress ──► built (build only)
                                   └──► verified
                 waiting ◄──────────────┘  (on blocked_request)
                      └──► ready           (on resolution)
                 escalated (terminal — requires a human)
```

A gate cannot start until its upstream gate reads `verified` in `status.json`.
Every write to `status.json` goes through the same protocol: `flock -x` on
`.agent-context/.lock`, then a `jq` patch to a tmpfile, then `mv` (atomic
replace). Never an in-place edit.

### 4.3 The intercom

Gate files encode *ordering*; the intercom encodes *clarification*. They are
deliberately separate channels. When a downstream agent hits an ambiguity it has
two bad options — guess (propagates a wrong assumption silently) or rewrite an
upstream gate file (breaks immutability). The intercom is the third option.

| Situation | Type | Action |
|---|---|---|
| Schema/requirement contradiction | `blocked_request` | Post, set own gate `waiting`, HALT |
| Test failure feedback to Build | `critic_feedback` | Post compressed trace |
| Non-blocking question | `clarification` | Post, continue |
| Answering a blocked_request | `resolution` | Post with `resolves` set |
| Pipeline-wide state change | `broadcast` | Post to all |

It is **JSONL, not JSON**, because an append to a file opened `O_APPEND` is
atomic at the OS level, whereas a read-modify-write on a JSON array is a data
race between two contending processes even under a lock.

Messages cap at 10KB — use `refs: ["file.md#L40"]` instead of pasting blobs.

### 4.4 Memory — two tiers

**Episodic** (`memory/episodic/<run_id>.jsonl`) is the raw event log: every
meaningful action, fix attempt, and discovery, each scored `importance` 1–10.
Written automatically by the PostToolUse hook and explicitly by agents.

Its operational payoff is loop prevention. Before retrying, an agent queries:

```bash
jq -c --arg ec "$ERROR_CLASS" 'select(.error_class==$ec and .outcome=="fail")' \
  .agent-context/memory/episodic/*.jsonl
```

If the same `error_class` already failed, it must try something different.

**Semantic** (`memory/semantic/*.md` — `boundaries`, `codebase`, `domain-rules`,
`pitfalls`) is durable distilled fact. Agents may **not** write it directly
during a turn; they propose by logging with `importance >= 8`, and the Reflector
consolidates when the summed importance since the last consolidation exceeds
150. Even then it writes `PENDING_CONSOLIDATION.md` — a human runs
`approve_consolidation.sh` to commit it. Learning is gated on a human.

### 4.5 Skills engine

A skill is a reusable procedure in `.agent-context/skills/<slug>/`. The
lifecycle is deliberately pessimistic:

1. Created with `self_verified: false` — invisible to `INDEX.md` lookups.
2. Run via `run_skill.sh`, which increments `success_count`/`fail_count` under
   lock and flips `self_verified: true` on first success.
3. Only then does it appear in `INDEX.md` for future agents to find.
4. The Reflector prunes entries where `fail_count > success_count` and unused
   for 7 days (de-indexes; does not delete the directory).

A skill that has never worked is never advertised.

### 4.6 The critic loop — the part that matters most

On **every** turn end, in **every** session (both lanes), `critic_gate.sh`:

1. Runs `test_command` from `project.md` — the real suite, not a claim.
2. **Green** (rc 0 or 5) → clear `.heal_state`, run the Reflector, `exit 0`.
3. **Red** → escalate immediately, no retries, if either:
   - `error_class ∈ {AuthError, PermissionError, PackageNotFound, PolicyViolation}` (non-transient), or
   - `last_fix_fingerprint == prev_fingerprint` (the same fix tried twice).
4. **Red otherwise** → read attempt counter from `.agent-context/.heal_state`;
   `> 3` writes an escalation summary and stops, else increment, print failures
   to stderr, `exit 2`.

`exit 2` is the mechanism: it blocks the stop and feeds stderr back to the
model. Returning `{"continue": true}` does *not* block — `continue` defaults to
true, and `continue: false` ends the turn outright with the message shown to the
*user* rather than the model.

Two design details worth knowing:

- The heal counter lives in `.heal_state`, owned by the hook — **not**
  `gates.test.heal_attempt`. A hook that waits for an agent to increment a
  counter blocks forever if the agent never does.
- You cannot satisfy this hook by editing `status.json`. Make the tests pass.

### 4.7 Compaction cascade

Reasoning degrades before the context window fills, so this is treated as a
correctness concern, not a cost one. Three layers:

1. **Truncation** of re-runnable tool output.
2. **`PreCompact`** archives the full transcript to `.agent-context/archive/`.
3. **`SessionStart(compact)`** re-injects the pin list — exact changed-file
   paths, the exact test command, live gate state, the archive path.

The pin list deliberately excludes `AGENTS.md` and the domain model: those are
re-read at session start anyway, and restating them spends the budget the
compaction was trying to reclaim. What it protects is the volatile detail a
summarizer destroys — turning `src/generation/query_handler.py:109` into "the
query handler file".

Project guidance: after correcting the same issue twice, the context is polluted
with failed approaches — `/clear` and re-prompt rather than `/compact`.

### 4.8 Worktree propagation

[.worktreeinclude](../.worktreeinclude) copies the hooks, scripts, and guides
into every git worktree. Without it a worktree gets tracked files only — and
since the canonical instructions and `.agent-context/` are gitignored here, an
agent there would start with no Stop hook, no test sensor, and no safety
instructions: isolated **and** unsupervised, the worst combination.

Deliberately excluded: `status.json`, `intercom.jsonl`, `memory/` (per-run state
— copying it makes two worktrees believe they are the same run), `skills/<slug>/`
(shared counters would race), and `.env`/`*.db`/`.venv`.

## 5. The agents

The seven pipeline roles are defined in
`.agent-context/agents/*.md`. These repository copies preserve the complete
authoritative legacy role bodies and add a small runtime adapter for Codex and
OpenCode. A Codex session may execute roles sequentially; logical role
boundaries do not imply isolated processes.

The model/tool columns below record the preserved source frontmatter. Codex
maps those fields to its available capabilities and configured effort; the
OpenCode wrappers select their DeepSeek models explicitly.

| Agent | Model | Effort | Tools | Writes |
|---|---|---|---|---|
| `plan` | sonnet | xhigh | Read, Write, Glob, Grep, AskUserQuestion, Edit | `plan.md` |
| `explore` | haiku | medium | Read, Write, Glob, Grep, Bash | `explore.md` |
| `build` | sonnet | high | Read, Write, Edit, Bash | source files in `plan.md` scope |
| `tester` | sonnet | medium | Read, Write, Edit, Bash | `tests/**` |
| `compressor` | haiku | low | Read, Write | `trace.md` |
| `code-reviewer` | sonnet | xhigh | Read, Glob, Grep, Bash, Write, Edit | `review.md` |
| `docs-writer` | haiku | low | Read, Write, Edit | `**/*.md` |

Effort is deliberately **not** minimized on `plan` and `code-reviewer`: higher
effort there lowers total cost by cutting heal iterations. A locked plan
compounds its errors downstream, and review is the last gate before a human.

`project.md` extends these with project-specific checks — e.g. the code-reviewer
gains `trace_id_propagation`, `qdrant_payload_schema`, `reranker_hard_reject`,
and `prometheus_metric_present`, each with a severity that maps to BLOCK or
REQUEST_CHANGES.

## 6. Multi-tool setup

Two CLI agents are configured against the same `.agent-context/` workspace.
They share the canonical `AGENTS.md` rulebook and repository role definitions,
but **not** their enforcement machinery.

| | Codex (primary) | OpenCode (secondary) |
|---|---|---|
| Instructions | `AGENTS.md` + `.agent-context/agents/<role>.md` | same shared files via repository wrappers |
| Config | `.codex/config.toml`, `.codex/hooks.json` | [opencode.json](../opencode.json), `.opencode/agents/*.md` |
| Hooks | PreCompact, SessionStart, SessionEnd, PostToolUse, one Stop critic | no automatic hook wiring; run critic manually before completion |
| Safety | sandbox/approvals plus mandatory `AGENTS.md` path and git boundaries | per-agent and global `allow`/`ask`/`deny` rules |
| MCP | own copy in `config.toml` | tool-specific configuration |

`opencode.json` defines its own seven agents with per-agent model, temperature,
step budget, and permission scoping. All seven currently route to DeepSeek:
`plan` and `build` on `deepseek/deepseek-v4-pro`, the other five on
`deepseek/deepseek-v4-flash`, with the key read from `{env:DEEPSEEK_API_KEY}`.
The `anthropic`, `openai`, and `ollama` provider blocks remain declared but are
no longer referenced by any agent.

**The gap that matters:** OpenCode has no automatic hook wiring. Its repository
agent wrappers and permission rules are present, but the acting OpenCode
session must invoke `.agent-context/hooks/critic_gate.sh` explicitly before
completion. Same rulebook, thinner sensor coverage.

Shared runtime memory lives in `.agent-context/memory/`. Any legacy memory under
`.claude/` or `~/.claude/` is historical only and is not read by the migrated
workflow.

## 7. How to use it

### 7.1 Everyday work (fast lane)

Just work. Ask for the change; the agent edits and verifies. The Stop hook runs
the suite at turn end and will not let the turn finish while it is red. Nothing
in `.agent-context/` is written.

This is the default and covers most tasks. You do not need to invoke anything.

### 7.2 Running the full pipeline

Start a run:

```bash
source .agent-context/scripts/new_run.sh
```

This prints a fresh `RUN_ID`, resets all gates to `pending`, archives the old
intercom, and preserves memory and skills. It must be **sourced** — it exports
`RUN_ID`, `AGENT_ROLE`, and `PROJECT_ROOT` into your shell, and `set -e` would
kill your terminal on any error.

Then advance one gate per turn. From the IDE, just ask:

> Run the plan agent for M7.

Or from the terminal:

```bash
AGENT_ROLE=build RUN_ID=run-2026-06-15-m6 codex "Run the build gate."
```

Order is enforced: `PLAN → EXPLORE → BUILD → TEST → REVIEW`, each gate blocked
until the previous reads `verified`.

Advancing gates one turn at a time from the IDE is **normal operation, not a
workaround.**

### 7.3 Checking where things stand

```bash
jq '{run_id, gates: (.gates|map_values(.status)), human_next_step}' \
  .agent-context/status.json
```

`human_next_step` is written by every agent before it halts and tells you the
exact next command. Right now it reads: run the build agent for M6 tasks 69–80.

For a plain-English summary, the project ships a slash command:

```
/code-space-simplifier
```

It reads the context files in a fixed priority order and returns a jargon-free
status and plan.

### 7.4 When the pipeline escalates

Escalation is terminal and needs you. `review.md` will contain an Escalation
Report: what was attempted each round, the current best hypothesis, and **one
specific answerable question**. Answer that question, then resume — usually by
posting a `resolution` to the intercom or by fixing the blocker yourself and
starting a new run.

Escalation happens on three conditions: three failed heal attempts, a
non-transient error class, or the same fix fingerprint tried twice.

### 7.5 Approving what the agents learned

After runs accumulate, the Reflector writes
`.agent-context/memory/episodic/PENDING_CONSOLIDATION.md`. Read it, delete
anything you disagree with, then:

```bash
bash .agent-context/scripts/approve_consolidation.sh
```

Only then does it reach `semantic/*.md` and start steering future runs. One
file is pending review now.

### 7.6 Switching tools mid-run

```bash
bash .agent-context/scripts/handoff.sh
```

Prints a context block to paste into the other tool's first prompt and writes
`handoff.md`. Because a tool switch changes which model works the gate, finish
a gate before switching, and drive quality-critical runs from Codex.

### 7.7 Which surface to use

| Use the IDE for | Use the terminal for |
|---|---|
| Single-gate invocations, reading, diagnosing, reviewing diffs | Multi-process runs (two tools contending on `flock`) |
| Anything where you read the result before the next gate | Headless/scripted Codex runs and CI |
| Editor selection arrives as context automatically | MCP OAuth (`/mcp`) |
| | Interactive git (`rebase -i`, `add -i`) |
| | Long unattended runs that must survive closing the editor |

The surface never changes the rules — only who drives the loop.

## 9. Known gaps and caveats

These are real observations from the installed files, not hypotheticals.

1. **Legacy Claude configuration remains on disk but is not runtime input.**
   The original global agent files and project `.claude/` settings were kept as
   migration provenance. Codex has one repository Stop critic path and no
   active Codex hook reads `~/.claude/`.

2. **OpenCode has weaker sensor integration.** Repository safety rules and role
   wrappers exist, but hooks are not automatic. Treat OpenCode runs as
   lower-assurance and prefer Codex for quality-critical gates.

3. **The learning loop has never closed.** Semantic memory is empty and no skill
   has been promoted, after 7 runs. The machinery works, but consolidation is
   human-gated and nobody has run `approve_consolidation.sh`. Until that
   happens the harness is not actually self-improving — only self-correcting.

4. **Six of seven episodic runs are `incomplete`.** Runs are being abandoned
   rather than closed out, which means `close_stale_runs.sh` will eventually
   rewrite them to `abandoned` and their lessons are never consolidated.

5. **OpenCode uses thin repository wrappers.** The wrappers intentionally point
   to `.agent-context/agents/*.md` instead of duplicating those complete role
   bodies. Do not regenerate them from global provider-specific definitions.

6. **`status.json` disagrees with reality** on M6 (see §8).

7. **The contract's §4.2 write protocol was aspirational — partially fixed.**
   No agent prompt reliably wrote `gates.<role>.status` itself; in interactive
   use the orchestrating session did that bookkeeping by hand between subagent
   calls, and a single headless `--agent X -p` invocation had no orchestrator
   to do it at all. `.agent-context/scripts/lock_gate.sh` is now the single
   writer for that transition (§11.5) and `critic_gate.sh` calls it
   automatically for the `test` gate on a green suite, so that one gate can no
   longer silently lag a passing run. `plan`/`explore`/`build`/`review` still
   require the agent to invoke `lock_gate.sh` explicitly at the end of its
   turn — there is no mechanical proxy for "this plan is good" the way there
   is for "this suite passed."

## 10. Quick reference

```bash
# Everyday: just work. Hooks handle verification.

# Start a pipeline run

# Run the sensor manually

# Full suite before committing
.venv/bin/python -m pytest tests/ -q

# Approve what the agents learned
bash .agent-context/scripts/approve_consolidation.sh

# Switch tools mid-run
bash .agent-context/scripts/handoff.sh

# Copy this harness to another project
bash .agent-context/scripts/bootstrap_new_project.sh /path/to/target
```

**Never:** hand-edit the `## Gate snapshot (auto)` block in `status.md`, write
to `.agent-context/.lock`, edit a gate file whose gate is `verified`, or try to
satisfy the Stop hook by editing `status.json`.

## 11. Daily workflow across sessions and tools

This section describes only how to *drive* the mechanisms in §1–10 day to day
— it defines no new state, and note §9.6 still applies: `status.json`'s
`gates`/`current_role` reflect the run-scoped architecture in
`.agent-context/runs/<run-id>/` (see `docs/agent_os.md`), which this document's
older §2/§4/§7/§8 examples predate; treat `.agent-context/scripts/` as the
current source of truth for exact invocations.

### 11.1 Resuming an existing pipeline from a brand-new chat

Open a fresh Codex or Claude Code chat in this repository and send:

> Resume the current repository workflow from repository state. Take the
> next valid gate only. Tell me ROLE, RUN and OBJECTIVE before acting.

Per AGENTS.md's session-bootstrap contract, the agent must run
`resume_run.sh` / `context_for_role.sh` and print `ROLE`/`RUN`/`OBJECTIVE`
before touching anything — it does not need, and must not rely on, this
chat's history. Verify those three lines match what you expect before letting
it proceed.

### 11.2 Starting a major new feature

```bash
bash .agent-context/scripts/new_run.sh --task "<exact objective>"
```
Then PLAN (any capable worker) → EXPLORE → BUILD → TEST → REVIEW, each locked
via `lock_gate.sh` (§9.7) before the next gate can claim. Use `handoff.sh`
when switching execution environment or tool.

### 11.3 Fast-lane patch

No new run. Give the task directly; the agent edits and verifies. Nothing
under `.agent-context/runs/` changes.

### 11.4 Switching tools mid-run

```bash
bash .agent-context/scripts/handoff.sh <role> --reason "..." --next "..." \
  --to-runtime <codex|claude|opencode> --to-provider <name> --to-model <id>
```
Recommended at provider/session boundaries. Not required between every gate
if the same session safely continues and repository state is already current.

### 11.5 Locking a gate

```bash
bash .agent-context/scripts/lock_gate.sh <plan|explore|build|test|review> \
  --owner <your-owner-id>
```
The only writer of `gates.<role>.status`/`locked_at`/`artifact_sha256`. Refuses
to re-lock an already-`verified` gate, and for `test` it reruns the real
`test_command` itself rather than trusting the caller.

## 12. Recommended provider routing (a default, not harness law)

Nothing in AGENTS.md or the scripts assigns a role to a specific provider —
any capable, available worker can run any role via
`start_claude_role.sh`/`switch_model.sh`/direct Codex or OpenCode invocation,
and `validate_context.sh` enforces gate order and lease ownership regardless
of who is asking. The table below is only a starting point for who to open
next:

| Gate | Suggested worker |
|---|---|
| PLAN | Codex |
| EXPLORE | Claude Code |
| BUILD | Claude Code |
| TEST | Claude Code |
| REVIEW | Codex |
| compressor / docs / mechanical work | local OpenCode model |

Deviate whenever a different worker is more available or better suited; the
gate machinery does not care.
